## `defineStep(options)`

Define a reusable, versioned step with typed input/output schemas.

```typescript
import { defineStep } from "@boboddy/sdk";
import { z } from "zod";

const myStep = defineStep({
  key: "my-step",
  name: "My Step",
  version: 1,
  description: "Does something useful.",
  additionalInput: z.object({ text: z.string() }),
  result: z.object({ summary: z.string(), score: z.number() }),
  signals: [
    {
      sourcePath: "score",
      key: "quality_score",
      type: "number",
      required: true,
    },
  ],
  agentPrompt: ({ input, env, boboddy }) => `
Analyze the provided text from ${input.text}.
Base URL: ${env.BASE_URL}
Write any generated files to ${boboddy.artifactsDir}
Return a summary and quality score.
`,
  status: "active",
});
```

### `StepDefinition` options

| Field             | Type                              | Required | Description                                                               |
| ----------------- | --------------------------------- | -------- | ------------------------------------------------------------------------- |
| `key`             | `string`                          | Yes      | Unique step key within the project                                        |
| `name`            | `string`                          | Yes      | Display name                                                              |
| `version`         | `number`                          | No       | Version (default: `1`)                                                    |
| `description`     | `string`                          | No       | Short description                                                         |
| `agentPrompt`     | `string \| ((context) => string)` | Yes      | AI instruction given to the executing agent                               |
| `additionalInput` | `ZodType`                         | No       | Additional input payload schema; fields are bound via the pipeline mapper |
| `result`          | `ZodType`                         | No       | Output payload schema                                                     |
| `signals`         | `Signal[]`                        | No       | Values to extract from the result                                         |
| `mcpServers`      | `OpenCodeMcpServers`              | No       | MCP server configs for tool-using agents                                  |
| `plugins`         | `OpenCodePluginEntry[]`           | No       | Opencode plugins merged into the step's execution config                  |
| `features`        | `StepFeature[]`                   | No       | Built-in feature plugins (e.g. `Features.notifications()`)                |
| `status`          | `"draft" \| "active"`             | No       | Draft steps are skipped by workers                                        |
| `executionMode`   | `"workspace" \| "no_workspace"`   | No       | `"no_workspace"` runs the agent without cloning your repo or a dev container; defaults to `"workspace"`. See [Execution mode](/boboddy/guides/steps/#execution-mode) |

### `agentPrompt`

`agentPrompt` accepts either a raw string or a function that receives a typed prompt context. The function form is recommended because it gives autocomplete for supported prompt variables and keeps prompt tokens consistent with your step schema.

```typescript
const browserReproStep = defineStep({
  key: "browser-repro",
  name: "Browser Repro",
  additionalInput: z.object({
    title: z.string(),
    description: z.string(),
  }),
  agentPrompt: ({ input, env, boboddy }) => `
Open ${env.BASE_URL}.
Reproduce the issue described in ${input.title}.
Save traces to ${boboddy.artifactsDir}trace.zip.
`,
});
```

#### Prompt context scopes

| Scope     | Example                   | Source                                                   |
| --------- | ------------------------- | -------------------------------------------------------- |
| `input`   | `${input.title}`          | Step execution input bound through the pipeline          |
| `env`     | `${env.BASE_URL}`         | Any defined environment variable available to the worker |
| `boboddy` | `${boboddy.artifactsDir}` | Boboddy-provided runtime values                          |

At runtime these become `{{input.title}}`, `{{env.BASE_URL}}`, and `{{boboddy.artifactsDir}}` inside the stored prompt template.

Boboddy currently provides:

- `boboddy.artifactsDir` for files that should be uploaded as step artifacts.

Legacy raw prompt tokens such as `{{title}}` and `{{stepArtifactsDir}}` still resolve, but new steps should prefer the scoped form.

### `Signal`

```typescript
type Signal = {
  sourcePath: string; // dot-notation path into result, e.g. "metrics.score"
  key?: string; // signal name used in advancement rules (defaults to sourcePath)
  type?: "number" | "string" | "boolean" | "object" | "array";
  required?: boolean; // fail execution if signal is missing
};
```

### `mcpServers`

`mcpServers` is a `Record<string, McpServerConfig>` where each value is one of three shapes:

```typescript
// Local subprocess server. `command` is [executable, ...args] — no separate `args` field.
type LocalMcpServer = {
  type: "local";
  command: string[];
  environment?: Record<string, string>; // {env:VAR} interpolates a worker env var
  enabled?: boolean;
  timeout?: number;
};

// Remote HTTP server.
type RemoteMcpServer = {
  type: "remote";
  url: string;
  headers?: Record<string, string>;
  oauth?:
    | { clientId?: string; clientSecret?: string; scope?: string; redirectUri?: string }
    | false;
  enabled?: boolean;
  timeout?: number;
};

// Enabled override — toggle an inherited server without redefining it.
type McpEnabledOverride = { enabled: boolean };
```

See [MCP servers](/boboddy/guides/steps/#mcp-servers) for examples, and
[Secrets](/boboddy/guides/steps/#secrets) for how `{env:VAR}` resolves and
where the real values live.

### `plugins`

`plugins` is an array of Opencode plugin entries merged into the step's execution config:

```typescript
type OpenCodePluginEntry = string | [packageName: string, options: Record<string, unknown>];
```

Entries are deduplicated by package name when combined with the baseline Opencode config.

### `Features`

`features` accepts built-in feature plugins from the `Features` namespace (imported from `@boboddy/sdk/definitions/steps`). A feature extends the step's `result` schema, appends signals, and injects prompt text.

```typescript
import { defineStep, Features } from "@boboddy/sdk/definitions/steps";

const step = defineStep({
  key: "repro",
  name: "Repro",
  agentPrompt: "Reproduce the bug.",
  features: [Features.notifications()],
});
```

| Feature                       | Effect                                                                                                                                            |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Features.notifications()`    | Adds a `$boboddy_notifications_v1` result array + signal (type `array`, not required) and prompt text for emitting user notifications.            |
| `Features.feedbackRequests()` | A real specialization of `notifications()` (not an alias): narrows every emitted item to `kind: "feedback_request"`, backed by the same `$boboddy_notifications_v1` signal. |

`Features` is exclusively for `features: [...]` attachment — value construction (`Notify`) and signal reading (`NotificationSignal`) are separate exports, kept apart on purpose so `Features.` autocomplete only ever shows things you attach to a step.

Each notification item is:

```typescript
// Inferred from the same zod schema `resultSchemaJson` is built from —
// there is no independently hand-written type to drift out of sync.
type NotificationItem = {
  kind: "feedback_request" | "status_update" | "blocked" | "result_ready" | "warning";
  title: string;
  body: string;
  priority: "low" | "normal" | "high" | "urgent";
  suggestedChannels?: ("in_app" | "work_item_platform_comment" | "email" | "slack")[];
  payload?: Record<string, unknown>; // feedback_request: { category, urgency, suggestedKey? }
};
```

### `NotificationSignal`

`NotificationSignal.key` is the raw `$boboddy_notifications_v1` signal key. `NotificationSignal.find(signals)` parses a step execution's signals array back into `NotificationItem[] | undefined`.

### `Notify`

A flat namespace of builder functions for constructing a notification result value at runtime — the same shape as `Rule`/`Computed` in `@boboddy/sdk/definitions/pipelines` — without hand-writing the object shape. Most useful inside a `codeStep()`'s `fn`, where there's no agent to follow the prompt instructions.

```typescript
Notify.create(item: NotificationItem);
Notify.inApp(title, body, priority, options?);
Notify.feedbackRequest(question, category, urgency, suggestedKey?);
Notify.merge(...fragments);
```

- `create` is the one generic constructor — field names match `NotificationItem` exactly.
- `inApp` is the only channel with dedicated sugar, because `in_app` is the only channel the platform actually delivers today; `work_item_platform_comment`, `email`, and `slack` are accepted by the schema as suggestions but currently have no delivery adapter. Use `Notify.create({ ..., suggestedChannels: [...] })` directly to suggest one of those.
- `feedbackRequest` is the value-builder counterpart to `Features.feedbackRequests()`.
- Each of `create`/`inApp`/`feedbackRequest` returns `{ $boboddy_notifications_v1: [item] }` — return it directly, or spread it into a larger result. `inApp`'s `options` is `{ kind?, payload? }`; `kind` defaults to `"status_update"`.
- `merge(...fragments)` combines multiple builder results into one.

See [Features](/boboddy/guides/steps/#features) for the guide.

## `codeStep(options)`

Defines a `kind: "code"` step: a plain function instead of an LLM prompt. Produces the same step shape `defineStep()` does, so it plugs into a `states[key].step` field unchanged.

```typescript
import { codeStep } from "@boboddy/sdk/definitions/steps";
import { z } from "zod";

export const sumScores = codeStep({
  key: "sum-scores",
  name: "Sum Scores",
  inputSchema: z.object({ scores: z.array(z.number()) }),
  resultSchema: z.object({ total: z.number() }),
  fn: ({ scores }) => ({ total: scores.reduce((a, b) => a + b, 0) }),
  signals: [{ sourcePath: "total", key: "total", type: "number" }],
  status: "active",
});
```

### `DefineCodeStepInput` options

| Field          | Type                                             | Required | Description                                                        |
| -------------- | ------------------------------------------------- | -------- | ---------------------------------------------------------------------- |
| `key`          | `string`                                          | Yes      | Unique step key within the project                                 |
| `name`         | `string`                                          | Yes      | Display name                                                        |
| `version`      | `number`                                          | No       | Version (default: `1`)                                              |
| `description`  | `string`                                          | No       | Short description                                                   |
| `fn`           | `(input) => result \| Promise<result>`            | Yes      | The step's implementation; must be a plain named export of the module `codeStep()` is called from |
| `inputSchema`  | `ZodType`                                         | No       | Zod schema for `fn`'s input                                          |
| `resultSchema` | `ZodType`                                         | No       | Zod schema for `fn`'s return value                                   |
| `signals`      | `CodeStepSignalSpec[]`                            | No       | Values to extract from the result; unlike `defineStep`, `type` is required (not inferred) |
| `features`     | `AnyStepFeature[]`                                | No       | Feature plugins from `Features`; only each feature's result extension and signals apply (no prompt on a code step) |
| `status`       | `"draft" \| "active"`                             | No       | Draft steps are not executed; defaults to `"active"`                |

`CodeStepSignalSpec` is `{ sourcePath, key?, type: "string" | "number" | "boolean" | "object" | "array", required?, availableWhenResultStatusIn? }`.

## `definePipeline(config)`

Define a pipeline as a flat map of named states — see [Building Pipelines](/boboddy/guides/pipelines/) for the full guide.

```typescript
import { definePipeline } from "@boboddy/sdk/definitions/pipelines";
import { z } from "zod";

const myPipeline = definePipeline({
  key: "my-pipeline",
  name: "My Pipeline",
  status: "active",
  input: z.object({ text: z.string() }),
  startAt: "run",
  states: {
    run: {
      kind: "step",
      step: myStep,
      input: (ctx) => ({ text: ctx.pipelineInput("text") }),
      next: "done",
    },
    done: { kind: "succeed" },
  },
});
```

### `DefinePipelineInput` options

| Field       | Type                  | Required | Description                                                       |
| ----------- | --------------------- | -------- | --------------------------------------------------------------------- |
| `key`       | `string`              | Yes      | Unique pipeline key                                                |
| `name`      | `string`              | No       | Display name (default: `key`)                                     |
| `version`   | `number`              | No       | Version (default: `1`)                                             |
| `description` | `string`            | No       | Short description                                                  |
| `status`    | `"draft" \| "active"` | No       | Draft pipelines are not executed                                   |
| `input`     | `ZodType`             | No       | The pipeline's own input schema; drives `ctx.pipelineInput(path)`'s typing |
| `startAt`   | `string`              | Yes      | The entry state's key. Must not name a `choice`/`succeed`/`fail` state |
| `states`    | `Record<string, PipelineState>` | Yes | Every state in the pipeline, keyed by its unique state key       |

### `PipelineState`

A discriminated union on `kind`, keyed by each state's own map key (there is no separate `dependsOn` — every incoming edge is derived from another state's own forward pointer):

| Kind | Shape |
| --- | --- |
| `step` | `{ kind: "step", step, input?, timeout?, blockWhen?, next }` |
| `choice` | `{ kind: "choice", choices?: [{ when, next }], default? }` |
| `fanOut` | `{ kind: "fanOut", step, over, maxConcurrency?, input?, timeout?, advanceEach, advanceAll, next }` |
| `parallel` | `{ kind: "parallel", branches: Record<string, { step, input?, timeout? }>, advanceAll?, next }` |
| `loop` | `{ kind: "loop", step, maxIterations, input?, timeout?, until, next, onExhausted }` |
| `succeed` | `{ kind: "succeed" }` |
| `fail` | `{ kind: "fail" }` |

`next` on a `step`/`fanOut`/`parallel`/loop-exit accepts either a state key (`string`) or `{ routeToPipeline: string, input?: Record<string, unknown> | null }` to hand execution off to a different pipeline. See [States](/boboddy/guides/pipelines/#states) for a field-by-field breakdown of each kind, and [Pipeline Advancement](/boboddy/guides/pipeline-advancement/) for `blockWhen`/`choices[].when`/`until` and `advanceEach`/`advanceAll`.

### `NodeInputCtx` — the `input` mapper's context

Every `step`/`fanOut`/`parallel`-branch/`loop`'s `input` mapper receives:

| Method                          | Description                                                              |
| -------------------------------- | ------------------------------------------------------------------------- |
| `ctx.pipelineInput(path)`        | Reads a dot-path out of the pipeline's own `input` schema                |
| `ctx.workItem.<property>` / `.field(name)` | Reads a top-level work-item property (`id`, `platform`, `title`, `url`, etc.) or a `fields`-bag field directly |
| `ctx.signal(nodeKey, signalKey)` | An earlier state's signal, addressed by that state's own key             |
| `ctx.output(nodeKey)`            | An earlier state's whole result output                                   |
| `ctx.signalsList(nodeKey)`       | A fan-out's whole cohort (every terminal branch's signals + output)      |
| `ctx.literal(value)`             | A fixed value that doesn't come from anywhere at runtime                 |
| `ctx.item`                       | **`fanOut` branches only** — the current branch's own item               |

`workItemTitle` and `workItemDescription` are bound automatically on every state; there is no separate pipeline-level default-binding layer — every mapper must supply everything it needs itself.

### `Rule` and `Computed`

Exported from `@boboddy/sdk/definitions/pipelines`, used by `blockWhen`, a `choice` branch's `when`, and a `loop`'s `until`:

```typescript
Rule.when(signalKey, operator, value);   // bare condition
Rule.signal(signalKey, operator, value); // leaf, for nesting in all/any
Rule.all([condition, condition]);
Rule.any([condition, condition]);
```

`operator` is one of `"equal" | "notEqual" | "lessThan" | "lessThanInclusive" | "greaterThan" | "greaterThanInclusive" | "in" | "notIn" | "contains" | "doesNotContain"`.

`Computed.average` / `.weightedAverage` / `.sum` / `.min` / `.max` / `.count` / `.booleanAny` / `.booleanAll` each take an array of **two or more** signal keys and return a token that can be passed as `Rule.when`/`Rule.signal`'s `signal` argument in place of a bare key. See [Pipeline Advancement](/boboddy/guides/pipeline-advancement/) for the full reference and examples.

## Fan-out and parallel cohort advancement

A `fanOut` state's `advanceEach`/`advanceAll` and a `parallel` state's `advanceAll` use a fluent, comparator-chain context distinct from the `Rule` DSL — see the [Fan-out guide](/boboddy/guides/pipelines/#fan-out-parallel-branches) for the state shapes and a full example.

### `advanceEach` context

Evaluated per-branch against that branch's own signals:

- **`signal(key)`** / **`stepSignals.<key>`** — the branch's own signal, typed against the step's declared signals. Chain a comparator (`.eq`, `.gt`, `.gte`, `.lt`, `.lte`, `.ne`, `.in`, `.notIn`, `.contains`, `.doesNotContain`) then `.then(outcome)`.
- **`all(...refs)` / `any(...refs)`** — group refs; terminate with `.then(outcome)`.
- `outcome` is restricted to `"continue" | "block"` (no routing).
- No computed-signal factories (`Computed.average`, etc.) — core has no mechanism yet to resolve a computed signal for a fan-out branch's policy.

### `advanceAll` context

Evaluated once per cohort, after every branch has settled:

- **`branchOutcomes.total()`** — the cohort's total branch count (fact `branchCount`). Returns a comparator ref.
- **`branchOutcomes.count(outcome)`** — a single outcome's count across the cohort (fact `${outcome}Count`). Returns a comparator ref.
- **`branchOutcomes.every(outcome)`** / **`.some(outcome)`** — `true` iff every/any branch resolved to `outcome`. Already a rule leaf — go straight to `.then(outcome)`.
- **`stepSignalsList.pluck(signalKey)`** — seeds an aggregation across every branch's `signalKey` value. Chain `.filter(operator, value)` / `.sortBy(direction?)` / `.unique()` to reshape, then exactly one reducer: `.count()`, `.sum()`, `.avg()`, `.min()`, `.max()`, `.booleanAll()`, `.booleanAny()`, `.join(separator?)`, `.first()`, or `.last()`. Returns a comparator ref.
- **`all(...refs)` / `any(...refs)`** — group refs; terminate with `.then(outcome)`.
- `outcome` in `.then(outcome)` is restricted to `"continue" | "block"`.

`BranchOutcome` (the `outcome` param to `branchOutcomes.count`/`.every`/`.some`) is `"continue" | "block" | "error" | "abandoned"` — the two additional values cover branches that failed or never ran.

## `defaultPipelineAssignment(callback)`

Define which pipeline is automatically started when a work item arrives. This goes in the reserved file `.boboddy/pipeline-builder/default-pipeline-assignment.ts`.

```typescript
import { defaultPipelineAssignment } from "@boboddy/sdk/definitions/pipelines";
import bugTriage from "./bug-triage";
import regressionReview from "./regression-review";

export default defaultPipelineAssignment(({ workItem, any, assign, skip }) => ({
  default: assign(bugTriage),
  rules: [
    any(
      workItem.field("status").eq("resolved"),
      workItem.field("status").eq("manual support"),
    ).then(skip()),
    workItem.title.contains("[urgent]").then(assign(bugTriage)),
    workItem.field("issueType").eq("bug").then(assign(bugTriage)),
    workItem
      .field("labels")
      .contains("regression")
      .then(assign(regressionReview)),
  ],
}));
```

The callback receives a context object. Only `defaultPipelineAssignment` needs to be imported.

### Callback context

| Property                       | Description                                                                                        |
| ------------------------------- | --------------------------------------------------------------------------------------------------- |
| `workItem.<property>`          | Comparator ref for a top-level work item property (`id`, `platform`, `title`, `url`, etc.)          |
| `workItem.field(name)`         | Returns a comparator ref for the named work item field (`fields` bag), typed via `field<TName, TValue>` |
| `context.isNew`                | Comparator ref; `true` when the work item is new             |
| `assign(pipeline)`             | Outcome: start the given pipeline (`PipelineDefinitionSpec`) |
| `skip()`                       | Outcome: do not assign any pipeline                          |
| `all(...refs)`                 | All nested conditions must match                             |
| `any(...refs)`                 | Any nested condition must match                              |

`workItem`'s top-level properties are `id`, `projectId`, `platform`, `platformId`, `platformKey`, `url`, `title`, `description`, `sourceCreatedAt`, `sourceUpdatedAt`, `createdByUserId`, `parentWorkItemId`, `createdAt`, `updatedAt`. `platform` is typed to the real platform literal union; the date-like fields are ISO strings (or `null`), not `Date` objects. See the [pipeline assignment guide](/boboddy/guides/pipeline-assignment/#work-item-properties) for details.

### Return value shape

| Field     | Type                           | Description                                                  |
| --------- | ------------------------------ | ------------------------------------------------------------ |
| `default` | `AssignOutcome \| SkipOutcome` | Outcome when no rule matches; `assign(pipeline)` or `skip()` |
| `rules`   | `AssignmentRule[]`             | Ordered rules; first match wins                              |

### Comparators

All comparators available on advancement `SignalRef`s are also available here: `.eq`, `.ne`, `.gt`, `.gte`, `.lt`, `.lte`, `.in`, `.notIn`, `.contains`, `.doesNotContain`. Not every comparator applies to every field — `.gt`/`.gte`/`.lt`/`.lte` only exist on numeric fields, so e.g. `workItem.title.gt(...)` is a compile error.

## API client

The SDK ships an auto-generated API client built from the OpenAPI spec.

```typescript
import { createBoboddyClient } from "@boboddy/sdk";

const client = createBoboddyClient("https://app.boboddy.dev");
```

Use `createStepDefinitionsClient` for CRUD operations on step definitions:

```typescript
import { createStepDefinitionsClient } from "@boboddy/sdk";

const stepClient = createStepDefinitionsClient("https://app.boboddy.dev");
```

## Config helpers

### JSONC parser

Parse `.boboddy/boboddy.jsonc` files (JSON with comments):

```typescript
import { parseJsonc } from "@boboddy/sdk";

const config = parseJsonc(rawString);
```

### Project config

Read the Boboddy project config from disk. `readProjectConfig` is exported from `@boboddy/worker` (not the SDK):

```typescript
import { readProjectConfig } from "@boboddy/worker";

const { projectId } = await readProjectConfig();
```
